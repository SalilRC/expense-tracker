# Expense Tracker Requirements

## 1. Overview

This project is a simple single-page expense tracker built with HTML, CSS, and vanilla JavaScript. It allows a user to record personal expenses, view them in a list, generate a summary report showing spending by category and the overall total, and import/export expenses using CSV files.

The app is intended to be lightweight, easy to run locally, and suitable for a no-backend, no-build-tools setup.

## 2. User Stories

- As a user, I want to add a new expense so that I can track my spending.
- As a user, I want to view a summary report so that I can understand how much I have spent by category and in total.
- As a user, I want to export all expenses to CSV so that I can keep or use a portable copy of my records.
- As a user, I want to import expenses from CSV so that valid records are added without replacing my existing expenses.

## 3. Data Model

Each expense entry should contain the following fields:

- ID: a unique identifier generated by the app; it is not included in the CSV columns
- Date: the date the expense was incurred
- Description: a short explanation of the expense
- Category: one of the predefined categories
- Amount: the cost of the expense

### Suggested Expense Structure

```json
{
  "date": "2026-08-06",
  "description": "Groceries for the week",
  "category": "Groceries",
  "amount": 42.50
}
```

## 4. Fixed Category List

The application must support the following fixed categories:

- Groceries
- Fuel
- Travel
- Eating Out
- Utilities
- Other

## 5. Functional Requirements

### Expense Input Form

The app must provide an input form on the same page as the report output.

The form must collect:

- Date
- Description
- Category
- Amount

### Validation Rules

The following validation rules must apply:

- Date is required.
- Description is required and should not be empty.
- Category must be selected from the fixed list.
- Amount is required and must be a positive number.
- The app should accept common shorthand values such as `26` or `25.1` and automatically normalize them to two decimal places for storage and display (for example, `26.00` and `25.10`).
- The form should prevent submission if validation fails.
- Invalid fields should be clearly indicated to the user.

### Behavior

- When the form is submitted with valid data, the new expense should be added to the in-memory collection or persisted to local storage.
- After adding an expense, the form should reset for the next entry.
- The report should update immediately after a successful submission.

### CSV Import and Export

- Export is entirely client-side and downloads `expenses.csv` with the columns `date`, `description`, `category`, and `amount` in that order.
- Exported CSV uses UTF-8 with a BOM, CRLF record separators, standard CSV quoting, and plain numeric amounts with exactly two decimal places and no currency symbol. An empty collection exports the header only.
- Import accepts UTF-8 CSV with CRLF or LF record separators, standard quoted fields, and an optional leading BOM. Required headers are exact and case-sensitive, are not whitespace-trimmed, and may appear in any order. Each required header must occur exactly once; additional columns are ignored.
- Imported data fields are trimmed for validation. Dates must be valid ISO calendar dates, descriptions must be non-empty, and categories must exactly match the fixed list after trimming.
- Imported amounts must use ordinary decimal notation: digits with an optional decimal point followed by digits. Signs, exponent notation, currency symbols, and thousands separators are rejected. Values are rounded half-up to two decimal places; amounts that round to zero or exceed `100000` before rounding are rejected.
- Valid rows are appended to the existing collection and saved to localStorage; invalid rows, including rows with the wrong field count, are skipped while valid sibling rows continue. The app reports accepted and skipped counts. Completely blank records are ignored.
- Every skipped nonblank row is identified by CSV record number and a specific correction reason, such as invalid date, blank description, unsupported category, invalid amount, or wrong field count.
- A header-only file named `expense-import-template.csv` is downloadable through a link labeled “CSV Import Template” beside the Import CSV button.
- Empty or unreadable files, malformed CSV, or missing/duplicate required headers produce a clear error and do not change the collection. A storage failure also leaves the in-memory collection unchanged and reports an error.
- The import control must be keyboard-operable, and import status/errors must be available to assistive technology.
- Automated tests must cover CSV acceptance scenarios and regression behavior for add/validation, report totals, persistence, edit, and delete.

## 6. Report Requirement

The app must provide a report that aggregates expenses by category and displays a grand total.

### Report Output

The report should show:

- Total spend per category
- Grand total across all categories

### Example Report Behavior

- Groceries: $120.00
- Fuel: $45.50
- Total: $165.50

## 7. Non-Functional Notes

- The app should run locally using a simple static server such as Live Server.
- No backend or database is required.
- Expense data may be stored in memory for the current session or persisted in localStorage for repeat visits.
- The implementation should remain simple and easy to understand for a beginner-friendly demo.

## 8. Page Layout Requirement

The input form and the report output must both be displayed on the same HTML page for the current version of the application.
